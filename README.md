# AI 智慧營運決策中樞

一家中部生鮮宅配商的營運決策系統原型。七個分析模組的輸出被翻譯成同一種格式，
由控制塔排出優先順序，再決定哪些交給機器、哪些必須由人判斷。

**網站** → `［部署後填入］`

---

## 這份東西想證明什麼

跑得動模型現在不稀奇。這裡真正想展示的是**知道什麼時候不該用它**：

| 決定 | 依據 |
|---|---|
| 十支商品，六支沒有用模型 | 礦泉水誤差 19.9% → 4.6% 值得；塑膠袋 10.6% → 13.4% 更差，退回原算法 |
| 丟掉信賴度最高的那批規則 | 塑膠袋出現在 23.5% 的訂單裡，以它為結果的規則提升度只有 1.03–1.18 |
| 不用最深的樹 | 深度 12 時訓練集 100%、驗證集反而從 92.9% 掉到 91.1% |
| 推薦一個成本更高也要採用的配送方案 | 直覺排法有 4 家門市送不進可收貨時段，貨要帶回來隔天再跑 |

四件事都先跑完才決定不用，不是省略。每一項都能在對應頁面上驗證。

## 目錄結構

```
.
├── index.html            控制塔 —— 今天最該處理的事
├── customers.html        誰在流失（決策樹 + 混淆矩陣 + 門檻試算）
├── basket.html           該推什麼（Apriori + 提升度陷阱）
├── voice.html            在氣什麼（客訴文本）
├── supply.html           賣多少缺多少（預測 → 庫存 → 缺口 → 配送重量）
├── delivery.html         怎麼送（CVRPTW + 時窗帶狀圖 + 產能壓力測試）
├── agent.html            不用人盯（DeepSeek tool use + 權限白名單）
├── method.html           方法、資料界線、聯絡方式
│
├── assets/               樣式與手寫 SVG 圖表（無任何外部函式庫）
├── data/                 由 pipeline 產生的 JSON，網頁只負責顯示
├── raw/                  原始 CSV，一個字沒有改過
├── pipeline/             產生 data/ 的 Python 程式
│   ├── build_static.py   進入點
│   ├── core/             各分析模組
│   └── requirements.txt
└── worker/               DeepSeek 金鑰代理（Cloudflare Worker）
```

## 怎麼重跑

網站是靜態的，但每個數字都由 `pipeline/` 實際計算產生。改資料重跑，全站一起更新。

```bash
pip install -r pipeline/requirements.txt
cd pipeline && python build_static.py
```

約 100 秒：決策樹重新配適、Prophet 對十支商品各回測一次、
Apriori 重新挖掘、OR-Tools 求解兩種配送方案再跑五個級距的壓力測試。

本機預覽（直接用檔案總管開 `index.html` 會被瀏覽器擋住讀取 JSON）：

```bash
python -m http.server 8000
```

## 分析模組

| 模組 | 方法 | 為什麼是它 |
|---|---|---|
| 流失預測 | scikit-learn 決策樹，深度 4 | 名單要交給客戶經理打電話，「為什麼是他」必須答得出來 |
| 需求預測 | Prophet ＋ 四種基準法 | 基準法不是陪跑，是用來判斷模型值不值得上線 |
| 商品關聯 | mlxtend Apriori | 規則能直接對應到促銷動作 |
| 庫存風險 | 缺口 × 前置期排序 | 缺得多又等得久的先下單 |
| 路徑最佳化 | Google OR-Tools CVRPTW | 容量、時窗、溫層可同時設為硬約束 |
| 客訴分析 | 痛點 × 情緒交叉 | 分類器負責縮小範圍，不負責下結論 |
| 值班代理 | DeepSeek V4 Flash ＋ tool use | 工具在瀏覽器本地執行，模型拿不到它沒開口要的東西 |

圖表全部是手寫 SVG，沒有引入任何前端函式庫——會議室網路擋掉 CDN 時，
圖表全白比圖表樸素嚴重得多。整個網站零外部請求。

## 資料界線

資料為課程情境模擬生成，不是任何真實企業的營運紀錄。這一點寫在網站上，沒有隱瞞。

比資料真假更重要的是**識別碼不能亂接**。這批資料裡有三套 `customer_id`：

| 體系 | 格式 | 實際是什麼 |
|---|---|---|
| 消費者 | `C0001`–`C1500` | 個人消費者 |
| 企業客戶 | `C001`–`C050` | 門市與企業客戶 |
| 配送節點 | `S01`–`S20` | 台中配送門市 |

字面交集 0 筆，但只差一位數。硬接的結果會是「某家量販店的平均客單價是 55 萬元」
這種在報表上很難解釋的數字。

商品也是兩套主檔。自動字串比對能找到 8 組疑似同物，其中「牛奶 → 牛奶咖啡 500ml」是誤配。
逐項核對後只有 **4 項**同時具備銷售預測與庫存紀錄，能真正貫通「預測 → 缺口 → 補貨 → 配送」。
橋很窄，但每一格都查得到出處。

## 值班代理的金鑰處理

`agent.html` 呼叫 DeepSeek，但**金鑰不在這個倉庫裡，也不在網頁裡**。

```
靜態網頁 ──呼叫──> Cloudflare Worker（金鑰在加密環境變數）──> DeepSeek
```

`worker/agent-proxy-worker.js` 是那支代理。它只做一件事：驗證通行碼與來源網域，
補上金鑰後轉送請求。它不碰任何資料——工具查詢全部在瀏覽器對本地 JSON 執行。

沒有通行碼、額度用完或服務異常時，頁面會自動切換成離線規則版，
執行完全相同的巡檢邏輯與工具呼叫，只是由程式判斷而不是模型。任何情況下都不會開天窗。
